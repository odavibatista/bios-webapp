> How real API responses are captured, stored and checked.

The responses come from a local API with real companies, captured by `scripts/capture-api.mjs`, not
from made-up data: the demo shows the API's real behavior, errors included.

The published version reads `public/presentation/v5`, with real API responses for 110,372 companies,
580,166 pieces of evidence and 86 sectors, generated by `scripts/build-presentation-data.mjs`. Company
records came from the official Receita dump and sanctions from official CGU files, processed by the
real API. The legal nature comes from Receita's `Empresas` file, in `legal-nature.json` in the dump. A record removed at the owner's request goes into `removed-cnpjs.json`, also in the dump, and stays out of a new version of the base. That list never goes into the repository. The end-to-end tests still use the fixture captures. Sector evolution holds 24 months:
the last one is the real API aggregate, and the earlier ones come from
`scripts/reconstruct-sector-history.mjs`, which reapplies the API's own rules to what existed at the end
of each month. Before writing, it reproduces the current index of every company, and generation fails
if they differ. The screen says the series is reconstructed. The main screen list
(`movements.json.gz`) holds the 5,000 companies with the most recent movements and every company
with an emissions movement, rebuilt with the API rule (UC15, rule 8) from the date of the recorded
fact. Each company file also holds the index evolution (UC07, RF36), computed with the bios-core-api
rules themselves: generation fails if a last step does not reproduce the current index.
`analytics.json.gz` keeps only each company's facts for the overview (UC19, RF37), with no name or CNPJ,
in the order of the search index, and `analytics-base.json.gz` holds the overview of the whole base, so
the main screen opens without downloading the index. The generator runs with
`node --experimental-strip-types`, because it reuses those rules from the app code, and takes the dump
and the bios-core-api folder.

`locations.json.gz` holds the 27 states and the 5,571 IBGE municipalities, for the municipality selector (RF38), and
is downloaded when the field is used. It comes from the bios-core-api catalog:
`node scripts/build-locations-data.mjs <bios-core-api>`.

- **One capture per file:** `src/app/core/mocks/fixtures/<operationId>/<scenario>.ts`, with
  `satisfies CapturedResponse<...>` over the generated type of the operation and status. If the API
  changes the shape of a response, `typecheck` rejects the old capture. The XLSX spreadsheet sits next
  to it as a file.
- **Manifest** (`fixtures/manifest.json`): bios-core-api commit, date of each phase, the demo account
  and the companies, with the reason for each one.
- **Nothing secret or personal:** passwords, tokens and the API key secret become placeholders before
  writing; the demo account uses the reserved `example.com` domain. `fixtures.spec.ts` rejects a CPF,
  an e-mail from another domain, a JWT and a key secret (INL02).

To capture again: a local API (bios-core-api `develop`) with a clean database, initial load, IBAMA
ingestion and GHG sync, and the API e-mails going to a Mailpit (`SMTP_HOST=localhost`,
`SMTP_PORT=1025` in the environment of whoever starts the API), where the script reads the links from.
Then:

```bash
BIOS_CAPTURE_PASSWORD=<password> BIOS_CORE_DIR=<bios-core-api folder> \
  node scripts/capture-api.mjs contas admin empresas setores limites
```

The phases and scenarios are in the script header. The `limites` phase blocks login from the IP for 15
minutes (RF20), so it runs last; `setores` is repeated in another month so the sector evolution series
has two real windows.
